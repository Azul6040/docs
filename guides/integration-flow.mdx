Connecting Restaurant Controller to Restaurantero Pro follows a predictable four-phase lifecycle: one-time branch setup, real-time data polling during service, a six-POST ingestion sequence at Corte Z time, and intelligence queries the following day. Understanding each phase and its trigger conditions will help you build a reliable, idempotent integration that handles network failures gracefully.

## Integration lifecycle overview

```
RESTAURANT CONTROLLER POS                    RESTAURANTERO PRO
─────────────────────────────────────────    ──────────────────────────────────

SETUP (one time per branch)
────────────────────────────────
1. Owner creates account in RP             → Group + Brand + Branch created
2. Owner generates API Key                 → rpro_live_xxx
3. Configure key in RC Settings            → RC is ready to send data

DURING SERVICE (real time)
─────────────────────────────────────
4. Manager views current shift sales       → GET /api/v1/live/sales/today
5. Manager views active shift alerts       → GET /api/v1/live/alerts/active

AT CORTE Z (each night)
──────────────────────────────────
6.  POST /api/v1/ingest/orders          ← product lines sold
7.  POST /api/v1/ingest/discounts       ← discounts and courtesies
8.  POST /api/v1/ingest/cancellations   ← cancellations and voids
9.  POST /api/v1/ingest/payments        ← payment method breakdown
10. POST /api/v1/ingest/sales           ← sales summary
11. POST /api/v1/ingest/cash-register   ← CORTE Z (triggers processing)

                                    → RP regenerates data cubes (async, ~5 sec)
                                    → Webhook: snapshot.completed
                                    → Alerts calculated automatically
                                    → AI daily insight generated

NEXT DAY (owner dashboard)
───────────────────────────────────────
12. GET /api/v1/intelligence/pnl        ← P&L for the previous day
13. GET /api/v1/intelligence/kpis       ← KPI traffic-light dashboard
14. GET /api/v1/intelligence/alerts     ← prioritized alerts
```

## Phase 1: One-time branch setup

<Steps>
  <Step title="Create the branch in Restaurantero Pro">
    The restaurant owner creates an account at `https://api.restauranteropro.com`. The platform sets up the hierarchy automatically:

    ```
    Group   → The restaurant group that owns the subscription
     └── Brand  → The concept or brand (e.g. "Pitic", "Mariscos El Faro")
           └── Branch → The physical location with its RFC, address, and timezone
    ```
  </Step>

  <Step title="Generate the API Key">
    From **Settings → Integrations → API Keys**, the owner generates a key scoped to the specific branch:

    ```
    rpro_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
    ```

    <Warning>The API Key is shown only once at generation time. If it is lost, generate a new key — the previous one is immediately revoked.</Warning>
  </Step>

  <Step title="Configure Restaurant Controller">
    Add the key and branch identifier to the `.env` file of the RC instance installed at that location:

    ```bash
    RESTAURANTERO_BASE_URL=https://api.restauranteropro.com/api/v1
    RESTAURANTERO_API_KEY=rpro_live_xxxxxxxxxxxxxxxxxxxxxxxx
    RESTAURANTERO_BRANCH_IDENTIFIER=b1c2d3e4-f5a6-7890-abcd-ef1234567890
    RESTAURANTERO_ENABLED=true
    ```
  </Step>

  <Step title="Verify the connection">
    Confirm that RC can reach Restaurantero Pro before the first Corte Z:

    ```http
    GET /api/v1/ping
    X-API-Key: rpro_live_xxx...
    ```

    A successful response confirms the branch is active:

    ```json
    {
      "data": {
        "type": "ping",
        "attributes": {
          "status": "ok",
          "branch_name": "Pitic",
          "plan": "pro",
          "message": "Conexión establecida correctamente con Restaurantero Pro."
        }
      }
    }
    ```
  </Step>
</Steps>

## Phase 2: Real-time polling during service

During active service, RC can poll the Live module endpoints to show the manager a live view of shift performance. These endpoints reflect the current shift — they do not depend on a completed Corte Z.

<CardGroup cols={2}>
  <Card title="Live shift sales" icon="chart-line" href="/api/live/sales">
    `GET /api/v1/live/sales/today` — Returns sales so far, covers, average ticket, and a projected day total. Poll every 5–10 minutes.
  </Card>
  <Card title="Active shift alerts" icon="bell" href="/api/live/alerts">
    `GET /api/v1/live/alerts/active` — Returns alerts generated during the current shift, such as unusually high discounts or a cash imbalance.
  </Card>
</CardGroup>

<Tip>Both endpoints only require `branch_identifier` as a query parameter. They do not count against ingestion rate limits.</Tip>

## Phase 3: Corte Z ingestion sequence

The Corte Z is the main integration event. When `CashRegisterOpening` transitions to status `completed` with type `zout`, send the following six POSTs **in this exact order**:

<Steps>
  <Step title="POST orders — product lines sold">
    Send every `OrderTicketLine` from closed orders for the day. Each line becomes an independent row that powers the Menu Engineering matrix, Star Employees ranking, and category sales reports.

    ```json
    POST /api/v1/ingest/orders
    X-Idempotency-Key: {closing.identifier}-orders
    ```
  </Step>

  <Step title="POST discounts — discounts and courtesies">
    Send all `Discount` records active during the shift. Excessive discounts trigger automatic alerts in the owner dashboard.

    ```json
    POST /api/v1/ingest/discounts
    X-Idempotency-Key: {closing.identifier}-discounts
    ```
  </Step>

  <Step title="POST cancellations — voids">
    Send all `Cancellation` records for the day. High cancellation rates trigger void alerts.

    ```json
    POST /api/v1/ingest/cancellations
    X-Idempotency-Key: {closing.identifier}-cancellations
    ```
  </Step>

  <Step title="POST payments — payment method breakdown">
    Send `Payment` records grouped by `PaymentType`. This data feeds cash reconciliation and the cash flow ledger.

    ```json
    POST /api/v1/ingest/payments
    X-Idempotency-Key: {closing.identifier}-payments
    ```
  </Step>

  <Step title="POST sales — day summary">
    Send the aggregated sales summary for the shift: total sales, food vs beverage split, covers, tables, and average ticket.

    ```json
    POST /api/v1/ingest/sales
    X-Idempotency-Key: {closing.identifier}-sales
    ```
  </Step>

  <Step title="POST cash-register — trigger processing">
    Send the `CashRegisterOpening` record last. This is the trigger that tells Restaurantero Pro the day is complete and cube regeneration should begin.

    ```json
    POST /api/v1/ingest/cash-register
    X-Idempotency-Key: {closing.identifier}
    ```

    <Warning>Send `cash-register` last. It triggers async cube regeneration. If it arrives before the other five POSTs, the P&L and KPIs will be calculated with incomplete data.</Warning>
  </Step>
</Steps>

### Complete six-POST sequence

<CodeGroup>

```php sendZOut() call order
// In RestauranteroProService::sendZOut()
$closingId = $closing->identifier;

// 1. Product lines first
$this->post('/ingest/orders',        $this->buildOrdersPayload($closing),        $closingId . '-orders');

// 2. Discounts
$this->post('/ingest/discounts',     $this->buildDiscountsPayload($closing),     $closingId . '-discounts');

// 3. Cancellations
$this->post('/ingest/cancellations', $this->buildCancellationsPayload($closing), $closingId . '-cancellations');

// 4. Payments
$this->post('/ingest/payments',      $this->buildPaymentsPayload($closing),      $closingId . '-payments');

// 5. Sales summary
$this->post('/ingest/sales',         $this->buildSalesPayload($closing),         $closingId . '-sales');

// 6. The Corte Z itself — triggers cube regeneration in RP
$this->post('/ingest/cash-register', $this->buildCashRegisterPayload($closing),  $closingId);
```

```http Required headers for every POST
X-API-Key: rpro_live_xxx
X-Idempotency-Key: {uuid}
Content-Type: application/json
```

</CodeGroup>

### Xout vs Zout

The trigger for which data you send depends on the closing type:

| Closing type | What to send | Effect in Restaurantero Pro |
|---|---|---|
| `xout` (Corte X) | Only `POST /ingest/cash-register` with `closing_type: "xout"` | Informational only — does not trigger cube regeneration |
| `zout` (Corte Z) | All 6 POSTs in order | Triggers full cube regeneration, alerts, and AI insight |

In Restaurant Controller, detect the closing type with:

```php
$isStoredZOut = $closingCategoryType === 'cash_register.closings.zout';
```

Fire all six POSTs immediately after this condition is met and RC completes its own internal close process.

## Phase 4: What happens async after the Corte Z

After receiving `POST /ingest/cash-register` with `closing_type: "zout"`, Restaurantero Pro responds with `202 Accepted` and begins asynchronous processing:

```json
{
  "data": {
    "type": "cash-register-ingest",
    "attributes": {
      "queued": true,
      "closing_type": "zout",
      "message": "Corte Z recibido. Los cubos del día se regenerarán en los próximos segundos."
    }
  }
}
```

Processing takes approximately 5 seconds and includes:

1. **Cube regeneration** — P&L, cash ledger, food cost, menu engineering, and KPI cubes are recalculated for the day.
2. **Alert evaluation** — Every KPI threshold is checked. Alerts are created for food cost, labor cost, cash variance, discounts, and cancellations that exceed configured limits.
3. **AI insight generation** — The Controllero Financiero agent generates a plain-language daily summary.
4. **Webhook dispatch** — The `snapshot.completed` event fires, telling your system the intelligence data is ready to query.

<Note>Use the `snapshot.completed` webhook rather than polling to know when P&L and KPI data is available. Register your webhook endpoint at `POST /api/v1/developer/webhooks`.</Note>

## Phase 5: Next-day intelligence queries

Once `snapshot.completed` fires, the owner dashboard can query the intelligence endpoints for the previous day's data:

| Endpoint | Returns |
|---|---|
| `GET /api/v1/intelligence/pnl` | Full P&L: food cost, labor cost, EBITDA, net profit |
| `GET /api/v1/intelligence/kpis` | All KPIs with traffic-light status vs industry benchmarks |
| `GET /api/v1/intelligence/alerts` | Prioritized list of alerts for the period |
| `GET /api/v1/intelligence/sales/summary` | Total sales, covers, avg ticket, shift breakdown |
| `GET /api/v1/intelligence/sales/by-employee` | Star Employees ranking |
| `GET /api/v1/intelligence/menu/engineering` | Menu Engineering matrix (Stars, Puzzles, Plowhorses, Dogs) |

All intelligence endpoints require `branch_identifier`, `date_from`, and `date_to` as query parameters.
